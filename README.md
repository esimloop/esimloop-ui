# esimloop-ui

A starter kit for apps and sites: **two design systems** — a data-dense application
layer and an editorial marketing layer — with **swappable themes** and an Astro scaffold.

```bash
npx github:esimloop/esimloop-ui mon-projet
cd mon-projet && npm install && npm run dev
```

Or, from a clone:

```bash
node bin/init.mjs ../mon-projet --name mon-projet --theme blank
```

## The one idea

**Skeleton and skin are separate files, and the split is enforced.**

| | Skeleton | Skin |
| --- | --- | --- |
| Files | `css/system.css`, `css/marketing.css` | `themes/*.css` |
| Contains | component rules, layout, states | token values only |
| Per project | never edit | **this is what you edit** |

`npm run check` fails the build if the skeleton declares a token, hard-codes a
colour — hex **or** functional, `rgb(0 0 0 / .5)` counts — or if any theme drifts
from the others. That guard is what makes themes genuinely interchangeable —
which is what stops every project you build from looking identical.

## Two layers

| | Application (`ds-`) | Marketing (`mk-`) |
| --- | --- | --- |
| Ground | neutral ramp | four warm bands |
| Accent | used throughout | used **once per page** |
| Largest type | 24px | 72px, fluid |
| Display weight | 600 | 500 |
| Button | 40px, weight 600 | 44px, weight 500, never a pill |
| Shadow | floating layers only | floating layers **and** the nav |
| Themes | light + dark | **light only** |

They share a typeface and nothing else. Don't mix their classes on one page.

## What you get

**47 components.** Application (17): shell, sidebar, button, badge, card, KPI card,
stat strip, score, tabs, field, alert, empty state, dialog, dropdown, toast, icon +
a 33-icon inline sprite.
Marketing (30): nav with mega-menu, announcement bar, hero (centered / split),
section, heading, split, card, quote, logos, stats, steps, tabs, CTA band, FAQ,
pricing, comparison table, team, media frame, footer, button, form field — plus a
content set: prose, article header, author byline, callout, table of contents,
article card, post navigation, breadcrumb, terminal.

**A living reference** at `/design-system` in every scaffolded project. It renders
the real components from source, so it cannot go stale: change a token and the
reference changes with it.

**6 themes**, all interchangeable: `blank` (neutral, AA-clean), `openseo` (the
reconstructed values) and `editorial` (paper, oxblood, sharp corners, elevated at
rest, serif headings) — each in an app and a marketing variant.

**A scaffold** with four working pages — landing, pricing, blog, dashboard — that
exercise every component, so a new project starts from something real rather than
an empty shell.

## What the third theme proved

`blank` and `openseo` are close cousins: grey ramp, blue accent, flat, 8px radius,
40px controls. If the split only worked between those, it would not really work.
`editorial` moves every structural axis at once — and `css/system.css` did not
change by one line:

| | blank | editorial |
| --- | --- | --- |
| Accent | `#1D4ED8` | `#7B2D3B` oxblood |
| Panel | `#FFFFFF` | `#FDFBF7` paper |
| Card radius | 12px | 4px |
| Card shadow | none | `0 1px 2px rgb(31 26 23 / .08)` |
| Button / input height | 40px | 44px |
| Heading face | Inter | a serif |
| Dialog backdrop | neutral black | warm `rgb(31 26 23 / .55)` |

Writing it also found four faults, which is the point of writing it:

1. **`--shadow-none` was named after its value.** A theme that wants elevation at
   rest cannot express it through a token called "none". Renamed `--shadow-rest`.
2. **`.ds-scrim` hard-coded `rgb(0 0 0 / .5)`.** The guard only scanned hex, so it
   sailed through. Now a `--scrim` token, and the guard reads functional notations.
3. **The guard counted tokens mentioned in comments.** Prose like "the theme sets
   `--depth: 0`" registered as a declaration and made two themes look like they had
   drifted. `declared()` strips comments first.
4. **Headings had no way to change face.** Added `--font-display`, which the other
   themes point at `--font-sans`, so nothing moved for them.

## Re-skinning a project

Open `src/design-system/themes/app-blank.css` and change four things:

1. `--accent` — your brand colour. Must reach **4.5:1** against `--surface-card`.
2. `--content` — your ink. Every text tier is this at an opacity, so it drives the
   whole grey scale.
3. `--surface-app` / `--surface-card` / `--surface-sunken` — the ramp.
4. `--font-sans`.

Everything else derives. For the marketing layer keep the *structure* even when the
values change: four close-together grounds separated by hairlines, and one accent used
once per page.

## Where this comes from

The system is a reconstruction of the OpenSEO open-source implementation (MIT), rebuilt
brand-neutral and domain-neutral. `docs/design-system.html` is the **origin audit**: it
documents where every value came from, so it stays SEO-specific on purpose. The kit
itself carries no domain vocabulary.

`themes/*-openseo.css` keep that name because it records provenance, not a use case —
they are a flat, border-driven skin that suits any dashboard.

## What the blank theme fixes

The reconstructed theme shares its four feedback hues between light and dark, tuned
against the dark ground. On white, `warning` (1.9:1) and `info` (2.6:1) fail AA as text.
`themes/app-blank.css` gives light and dark their own sets, all AA as text — measured
ratios are in the comments. If you use `app-openseo.css`, follow the constraint in
section 09 of the audit: semantic hue as fill, border or dot, label in the foreground
colour.

## Deliberate choices worth knowing

- **Severity is three tiers, not five** (`critical` / `warning` / `info`, plus passed).
  The palette has no fifth semantic hue.
- **Mobile tables scroll horizontally.** Not reflowed into cards, no columns dropped —
  these tables exist to be compared across. Mark the identifier column `data-col="id"`
  so it keeps a readable width.
- **The marketing layer is light-only.** Adding a dark mode is a design project, not a
  token swap: the four warm grounds have no automatic dark equivalents.
- **The sidebar does not collapse.** It is either present (≥768px) or a drawer.

## Verified

Node 24.20.0 · Astro 7.3.2. `example/` installs and builds clean (8 pages); checked at
1280px, 800px and 375px, in dark mode, and under both the `blank` and `editorial`
themes — no overlaps, no overflow, no clipping in any combination. On
`/design-system`, the application panel follows the theme while the marketing islands
stay light. The dialog, dropdown and toast were driven through their real behaviour:
top-layer entry and focus movement, arrow/Home/End/Escape menu navigation and focus
return, and live-region insertion and dismissal.
